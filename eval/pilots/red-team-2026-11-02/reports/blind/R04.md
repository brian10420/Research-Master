### A1 (load-bearing) — Decomposition look-ahead is unguarded

- Claim attacked: RESEARCH_STATE.md:37-41 (C1), :42-46 (C2), :50-53 (C4) — every Tidewater
  test MASE; and PROTOCOL.md:10-11 "The test window is never read during training or
  checkpoint selection; it is scored once per run by `scripts/eval_test.py`".
- The hole: PROTOCOL.md:17 defines the arm as "seasonal-trend decomposition + MLP on the
  residual". A seasonal-trend decomposition is, in its common forms, a two-sided smoother:
  the trend and seasonal components at hour h use hours after h. If, at scoring time, the
  decomposition is fitted over the test window (or over the full series) and the MLP only
  forecasts the residual, then the reconstructed forecast at origin + 24 h contains
  information from hours after the origin. The leak guard at PROTOCOL.md:10-11 is scoped
  to "training or checkpoint selection"; the scoring path's decomposition is not covered
  by any sentence in the four files, and none of the four files says the decomposition is
  one-sided / fitted only on history up to each forecast origin.
- Evidence that it is a hole: the absence quoted above (PROTOCOL.md:10-11 and :17); no
  occurrence of "causal", "one-sided", "history only" or an equivalent anywhere in the
  bundle (grep over the four files). The numbers neither confirm nor exclude a leak: the
  fold-3 val→test gap is larger for Tidewater (+0.098) than for GBT (+0.083) (seed means,
  ledger rows 33-35 vs 46-48), which is the opposite of what a future-seeing decomposition
  would produce on a holiday shift, so this is an untested assumption, not a demonstrated
  leak.
- Severity: load-bearing. If the decomposition is non-causal, C1's −0.263, C2's −0.016 and
  C4's fold-3 ordering all move in Tidewater's favour by an unknown amount; a reviewer in
  forecasting asks this question first.
- Cheapest test: read the inference path of `train_tw.py` / `scripts/eval_test.py` and
  confirm the decomposition for each forecast origin uses only hours ≤ origin (10 minutes,
  no compute). If the code is ambiguous: re-score one existing checkpoint (RUN_017, fold 1,
  seed 7) with the decomposition refitted strictly on history at each origin and compare
  to 0.721 (ledger row 39); one CPU run of minutes. If the number is unchanged, add one
  sentence to PROTOCOL §1 and the paper; if it moves, every Tidewater row must be rescored
  under new ledger rows.

### A6 (minor) — The four folds are not independent; fold 4's validation window is 75 % fold 3's test window

- Claim attacked: PROTOCOL.md:36-39 "the four fold-paired differences are tested with a
  paired two-sided t-test (n = 4)"; RESEARCH_STATE.md:44 "95% CI −0.039 to +0.007".
- The hole: from PROTOCOL.md:5-8, fold 3's test window is [2025-11-24, 2026-01-19) and
  fold 4's validation window is [2025-12-29, 2026-01-26): 21 of fold 4's 28 validation
  days are fold-3 test days, and 35 days of fold 3's test window sit inside fold 4's
  training set. Fold 4's training set is a superset of fold 3's; the fold differences are
  positively correlated, so the t-test's n = 4 is an overstatement of the effective sample
  and the C2 interval is, if anything, too narrow. It also means fold 4's checkpoint
  selection and GBT early stopping (PROTOCOL.md:26-27) were decided on a window that
  contains New Year's Day while fold 4's test window contains no holiday.
- Severity: minor. For C1 the effect is 2.5× the margin in every single fold, so no
  correction changes it; for C2 a wider interval is still "inconclusive". Rolling-origin
  overlap is standard practice, but the paper should say the folds overlap and the test
  is approximate.
- Cheapest test: a sentence in the paper; optionally report a block-bootstrap or a
  per-fold table (already present) instead of a t-based CI. Zero compute.
